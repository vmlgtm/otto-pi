Phase 4 Handoff: Container Sandbox for otto-pi

Written 14 Oct 2026 · Prerequisites: Phases 1–3 merged to main (commits d8a4f81, a5b71a3, 7e9c00b) · Branch: feat/phase-4-container-sandbox · Follows the format of docs/PHASE_3_MULTI_AGENT_HANDOFF.md

Give Otto a real Linux container, driven from its own Durable Object, so it can clone large repos, install dependencies and run real test suites. Today it can do none of these. Every later phase (Bitbucket, observability, evals) depends on this one, so it is the only phase specified in full here. The later phases are outlined in section 10.

Replace, don't run side by side. Otto isn't live for any users, so there's no staged rollout, no feature flag, and no compatibility with existing sessions. The container replaces the @cloudflare/computer workspace outright.

1. Why this phase comes first: Otto cannot clone big repos or run tests

Each point below was observed directly. None is a guess.

ObservationEvidenceConsequence
A shallow clone of a ~1 GB repo crashes the Durable Object. Workers Logs, 14 Oct 2026, 11:03:02 UTC: "Durable Object exceeded its CPU time limit and was reset" after 32.5 s of CPU, while running git_clone of vmlgtm/wp-calypso with depth: 1. A retry burned another 10.3 s and then stalled. Git runs in JavaScript inside the Worker (@cloudflare/computer + isomorphic git), and unpacking the download is CPU-bound. Raising the CPU limit would not fix the next problem.
After the reset, the UI showed "Running git_clone" indefinitely. git_clone is replay: "unsafe" (src/git-tools.ts:81), so pi does not rerun it after a reset. Nothing reports the failure to the client. Logs show 30-second wake-ups at ~0 ms CPU afterwards. A tool killed by a reset must end in a visible error. This is in scope (Component E).
Otto never ran the tests on its one real fix. PR vmlgtm/ufo#3 says: "All existing test cases are unaffected (verified by tracing through each one)." exec runs a single ES module in an isolate with no shell, no npm install and no network (src/workspace.ts:26). The Phase 1 self-correction loop cannot work on any repo that has dependencies.

Every comparable agent (Claude Code, OpenAI Codex cloud, the GitHub Copilot coding agent, Devin, OpenHands) gives the model a full shell in a container or VM. It installs dependencies once from a setup script, caches the result, and runs the real test commands. This phase brings Otto in line with them while keeping what it already does well: durable sessions, streaming, guardrails and subagents.

3. Target architecture: one container per session, one filesystem, and tokens injected outside it

Browser ──WebSocket──▶ PiAgent (Durable Object, one per session)
                         ├─ pi-durable harness, sessions, subagents   (unchanged)
                         ├─ guardrails, token redaction               (unchanged)
                         ├─ tools ──────────────┐
                         │                      ▼
                         │            ContainerEnv  (our pi ExecutionEnv adapter)
                         │                      ▼
                         │            this.ctx.container  (Sandbox SDK 1.0)
                         │              ├─ exec(argv, {cwd})  → bash, git, npm, tests
                         │              ├─ Files               → file reads and writes
                         │              └─ snapshot            → skip reinstall next time
                         └─ outbound handler ◀── container's HTTP(S) to github.com etc.
                              adds the token here; the container never holds it
One filesystem, not two. Today, read/write/edit/ls/find/grep and every git_* tool operate on the @cloudflare/computer virtual filesystem at /workspace. If the repo is cloned inside the container, those tools cannot see it. Move all file and git tools onto the container, and remove @cloudflare/computer (see production readiness). Do not keep both: a split workspace would leave the model editing files that tests never see.
Decision: use pi's built-in tools through an ExecutionEnv adapter. pi-durable 1.1.0 ships read, write, edit and bash (@earendil-works/pi-durable/tools, exported together as CodingTools). They work on whatever ExecutionEnv the harness provides (HarnessOptions.env). Write one adapter, ContainerEnv, that implements ExecutionEnv (FileSystem + Shell, in pi-durable/env) on the Sandbox container. Then pi maintains how the tools behave (edit matching, output limits, writing long output to a file), and we maintain only the adapter.
  • Test the adapter with pi's own suite, createEnvConformance() from pi-durable/testing.
  • Size it honestly. Simple methods map onto Files or a fixed exec argv. Some are stateful: openBinaryReader must keep reading the same file even if it's renamed, and openTextLineReader and openDirReader are cursors. Shell.exec must support onOutput streaming, the output window/skipped accounting and spill to a file. Budget for this; it's the largest piece of the phase.
  • watch is exercised by the conformance suite (dist/testing/env-conformance.js), and EnvConformanceOptions has no skip option. Either implement a simple polling watch (preferred; mode: "polling" is allowed), or drop the watch cases from the returned list by name and record which ones in NOTES.md.
  • createBashTool({ prepare }) runs before every command. Use it to set the working directory and remove credentials from the environment.
  • We write three read-only tools that pi doesn't have: ls, find and grep. They're for the Explorer, which must search without a shell. Each runs a fixed argv (e.g. ["grep", "-rn", "--", pattern, path]), never shell text.
  • Rejected: computer's own container backend. It's a preview and isn't meant for monorepos.

4. Scope of work

Component A: container image and config

  • A Dockerfile in the repo root. Use a Debian-based Node image with git, ca-certificates, coreutils (for timeout) and corepack enabled, so npm, yarn and pnpm all work. Calypso needs Node 24 and 1mg_web needs Node 22. Use a Node 24 base and install Node 22 alongside it, or document how to switch versions per repo.
  • Copy in the SDK's sandbox-shim: COPY --from=docker.io/cloudflare/sandbox:<version> /usr/local/bin/sandbox-shim /usr/local/bin/sandbox-shim. The tag must match the installed @cloudflare/sandbox version. A mismatch causes SandboxProtocolError.
  • In wrangler.jsonc, add a containers entry for class_name: "PiAgent" with scheduling_policy: "durable_object" and a named image (e.g. images.workspace). Mirror it in the env.test and previews blocks where needed.
  • Add @cloudflare/sandbox (1.x) to package.json, pinned to an exact version that matches the Dockerfile tag.
  • Pin @earendil-works/pi-durable to 1.1.0 (today: ^1.0.0). CodingTools and the conformance suite are 1.1.0 features.

Component B: container lifecycle in PiAgent

  • Start lazily on the first tool call that needs the container, not on connect.
  • Prepare the repo in a separate step through a prepare_workspace tool (or host-side code), not the general shell:
    1. Start the container with internet on.
    2. Shallow clone.
    3. Install dependencies.
    4. Save a snapshot (public beta in 1.0), only when a setting such as SANDBOX_SNAPSHOTS=on is set. When it's off, or a restore fails, fall back to a fresh install.
    5. Restart with internet off for the rest of the session.
    Store the snapshot handle in DO storage, keyed by repo and commit, so the next session for the same commit skips the install.
  • prepare_workspace owns cloning. Remove git_clone as a model tool, because a clone needs internet. If a fix needs a new dependency, the model calls prepare_workspace again with an install step. That turns internet on for the install command only, then off again. Internet is never on while the model's own bash commands run.
  • Stop the container when the session's run ends, and after an idle period (suggest 10 minutes) through the existing Lifecycle/alarm machinery. Never leave a standard-4 container running overnight.
  • Survive resets. Long commands such as installs and full test runs must not depend on one tool call staying alive:
    • Alarm handlers have a 15-minute wall-time limit (NOTES.md, "Alarm wall time").
    • A deploy kills in-flight work after 30 seconds.
    Run commands longer than about 2 minutes as background processes inside the container, writing output to a file. The tool then waits on or polls that process and can pick it up again after a reset. Whether the container itself survives a Durable Object reset is to be verified.

Component E: interrupted tools must end in a visible error

When an unsafe tool call is cut off by a reset or eviction and pi will not replay it, the UI card must change from "Running" to a failed state with a plain message (e.g. "Interrupted: the session restarted while git_clone was running"). Emit the same fact as a structured log line. Reproduce it first with the Calypso clone on the current code, before the container lands, so the fix is proven against the real failure.

5. Guardrails: none of the current protections may be lost in the move to a real shell

1. Git guardrails carry over, and the shell cannot bypass them. Keep, in the new git tools: the otto/ branch regex, the protected-branch block (main, master, release, production), the force-push block and drafts by default for PRs. With bash, the model could just run git push itself. A command denylist alone is not enough, so enforce this at the credential layer instead (next item).
2. Tokens never enter the container. Use the Sandbox 1.0 outbound handler to add credentials to requests as they leave the container. Do not put tokens in clone URLs or environment variables. The handler should add a write-capable token only to a push (git receive-pack) that git_push has explicitly allowed for that one branch. Every other request goes out with no credentials. The test repos are public, so clones need none, and no read-only token exists today. When private repos come (Phase 5), add a separate read-only token and give it only to fetches. Then a push typed into bash fails for lack of credentials. Also strip any credential variables in createBashTool's prepare hook. Keep the current "token never reaches model context" rule and the exact-value redaction list in src/server.ts:145.
3. Internet only during setup. Cloudflare's own docs warn that enableInternet: true also lets the repo's install and test scripts reach the internet. Allow it for clone and install only. Run the model's bash commands with internet off, except for the outbound handler's allowed git hosts. Confirmed in the Durable Object Container API docs: with enableInternet: false, intercepted hostnames still resolve and are routed to the handler, and every other lookup times out.
4. Limits stay explicit. Per-command timeout of 600 s at most. Output cut off at 50 KB. Container stopped on idle. At most one container per session: subagents share the session's container, as they share /workspace today.

7. Definition of done

  1. The ufo fix is re-solved with real tests. In a fresh session on vmlgtm/ufo, Otto reproduces issue #1 with a failing test, fixes it, and shows vitest passing in the tool output. A PR description that says "verified by tracing" counts as a failure.
  2. Calypso clones and tests. vmlgtm/wp-calypso clones (depth 1), installs, and runs one package's Jest tests in the container, with no Durable Object reset in Workers Logs.
  3. Calypso measurements are recorded in NOTES.md: clone time, install time, peak memory, disk used, snapshot size, restore time, test time and container cost for the run.
  4. The guardrails hold. Running git push origin otto/x through bash fails for lack of credentials. git_push to main is still blocked. The token appears in no transcript, tool result or log.
  5. An interrupted tool ends in a visible error, not a spinner (Component E).
  6. Containers stop at the end of a run and on idle. wrangler containers list shows none left running after a session ends.
  7. No model-facing tool depends on @cloudflare/computer, and the package is gone from package.json.
  8. Otto works with snapshots switched off. Snapshots are a speed-up, not a requirement.
  9. pnpm run typecheck, pnpm run test and pnpm run build pass. Today's baseline is 54 tests in 8 files, all passing (15 Oct 2026). Port every guardrail, redaction and multi-agent test to the new tools. Delete a test only if its feature is deliberately removed (e.g. JavaScript-only exec), and note why in the PR.

  • Tools: bitbucket_create_pull_request (POST /2.0/repositories/{ws}/{repo}/pullrequests, draft: true, target branch taken from the repo's mainbranch, never a hard-coded main), bitbucket_add_pr_comment, and bitbucket_get_pipeline_status.

Phase 6: sessions index, run log and cost

Gate: none beyond Phase 4. This phase can run in parallel with Phase 5.

  • Sessions are invisible after "New session". The client keeps only the current id in localStorage (src/client.tsx:68, :598), and webhook-started sessions never appear. Add a D1 sessions table (id, repo, ticket, branch, PR URL, status, start/end, tokens in/out, model calls, cost), a GET /api/sessions route and a sidebar.
  • Run log: one structured JSON log line per agent event (run start/end, tool name, duration, whether it failed, subagent start/finish, PR opened). Workers Logs makes JSON fields searchable. Today the code emits about eight console.warn lines in total.
